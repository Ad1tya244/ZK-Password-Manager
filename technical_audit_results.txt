TECHNICAL AUDIT REPORT — ZERO-KNOWLEDGE PASSWORD MANAGER
Date of Audit: June 23, 2026

================================================================================
EXECUTIVE SUMMARY
================================================================================
Overall Score: 6.5 / 10
Status: NOT PRODUCTION-READY

While the Zero-Knowledge client-side cryptography, Next.js route migration, and
TypeScript build integration are solid and build cleanly, the system is not 
ready for production due to two critical issues:
1. Unsalted/Lookup-Direct Account Recovery (Database Leak Threat)
2. Infinite Rate-Limiter Map Growth (DoS Memory Leak)

Addressing these security and stability blockers will elevate the application
to a production-grade standard.

================================================================================
CRITICAL ISSUES
================================================================================
1. Unsalted/Lookup-Direct Account Recovery (Database Leak Threat)
   - Risk: High
   - Description: The client hashes the recovery key using HKDF (producing
     recoveryKeyHash) and sends it to the server. The server stores this exact
     hash string directly as a database column in plaintext. During recovery,
     the server queries the database by matches of this hash. If the database
     is compromised, an attacker obtains all recoveryKeyHash values. Since the
     endpoints /api/auth/recovery/init and /api/auth/recovery/reset authenticate
     solely by finding these values, anyone with access to the database dump
     can immediately recover any account and reset its master password.
   - Suggestion: The server must hash the client-supplied recoveryKeyHash (e.g.,
     using SHA-256 or bcrypt) before storing it, and apply the same hash
     function to incoming request payloads before querying or validating.

2. Infinite Rate-Limiter Map Growth (DoS Memory Leak)
   - Risk: High
   - Description: The local rate limiter uses a global in-memory Map store
     (const store = new Map<string, RateLimitEntry>();) that grows indefinitely.
     While expired items have their counters reset upon subsequent requests from
     the same key, keys are never evicted or deleted from the Map once added.
     An attacker performing a distributed attack using many distinct IP
     addresses can inflate this map indefinitely, consuming memory until the
     Node process crashes with an Out of Memory (OOM) error.
   - Suggestion: Introduce a cleanup interval to prune expired entries, use an
     LRU eviction policy cache, or migrate rate limiting to a Redis/Upstash
     implementation suited for serverless.

================================================================================
MEDIUM ISSUES
================================================================================
1. No .env.example Documentation
   - Risk: Medium
   - Description: The project lacks a .env.example template to instruct
     developers and deployment environments on what environment variables
     (like DATABASE_URL and JWT_SECRET) must be set.
   - Suggestion: Add a root .env.example template.

2. 2FA Persistence after Recovery
   - Risk: Medium
   - Description: If a user resets their credentials using the recovery key,
     their twoFactorSecret remains active. If they lost their 2FA device, they
     are still locked out. If this is intentional, it must be documented;
     otherwise, it is a user lockout vector.
   - Suggestion: Explicitly decide if recovery should disable 2FA. If 2FA is
     preserved, warn the user during setup. If not, reset twoFactorSecret to
     null during recovery resets.

================================================================================
MINOR IMPROVEMENTS
================================================================================
1. Loose 'any' Types
   - Risk: Low
   - Description: TypeScript uses 'any' for decoded token objects and some
     state items in components, weakening type safety.
   - Suggestion: Define explicit interfaces and remove any.

2. Check-Then-Mutate Database Queries
   - Risk: Low
   - Description: Vault update and delete queries check if an item exists first,
     then update/delete by ID.
   - Suggestion: Use a single update/delete statement with composite conditions:
     prisma.vault.update({ where: { id, userId }, data }) to avoid race conditions.

3. Workspace Cleanup
   - Risk: Low
   - Description: The unused apps/api workspace folder is still in the codebase.
   - Suggestion: Delete the unused apps/api folder completely.

RECOVERY FLOW
--------------------------------------------------------------------------------
[PASS] Recovery keys are randomly generated.
  - Why: Hex key representation is derived using 32 random bytes from window CSRNG.
  - Files: apps/web/src/utils/encryption.utils.ts#L15-L23
  - Risks: None.

[FAIL] Recovery keys are hashed before storage.
  - Why: The server stores the client-provided recoveryKeyHash directly in
    the database in plaintext. If the database leaks, an attacker obtains
    all recoveryKeyHash values and can bypass password authentication by resetting
    passwords directly.
  - Files:
    * apps/web/src/lib/services/auth.service.ts#L140-L191
    * apps/web/src/app/api/auth/recovery/init/route.ts
  - Risks: High Risk. Database disclosure allows attackers to recover any user's
    account and reset their master password.
  - Fix: Hash the recoveryKeyHash value server-side before database storage and
    before lookup matching.

[PASS] Plaintext recovery keys are never stored.
  - Why: Only client-derived tokens are written to DB paths; the master seed hex
    stays client side.
  - Files: apps/web/src/utils/encryption.utils.ts#L25
  - Risks: None.

[FAIL] Recovery verification is secure.
  - Why: Verification relies entirely on finding the plaintext-equivalent
    recoveryKeyHash in database records.
  - Files: apps/web/src/lib/services/auth.service.ts#L153-L175
  - Risks: High Risk. (Same database leakage vulnerability as above).
  - Fix: Perform secure server-side hashing on all recovery lookup parameters.

[PASS / WARNING] Recovery reset invalidates previous credentials.
  - Why: Replacing the master password updates user hashes and client keys, but
    does not clear twoFactorSecret properties.
  - Files: apps/web/src/lib/services/auth.service.ts#L178-L190
  - Risks: If a user loses their 2FA device, recovery resets still lock them out
    upon logging in.
  - Fix: Explicitly reset twoFactorSecret to null during recovery resets if 2FA
    should be disabled during account recovery.
